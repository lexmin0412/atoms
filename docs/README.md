# 文档索引与迭代约定

本目录用于沉淀**规范**与**每次迭代的方案**。

## 目录结构

```
docs/
├─ README.md                 # 本文件：索引与约定
├─ architecture.md           # 系统架构（长期，持续更新）
├─ roadmap.md                # 路线图与已知限制（长期，滚动更新）
├─ security-audit.md         # 安全专项审计（滚动更新：发现 → 修复状态）
└─ iterations/               # 每次迭代一份方案文档（append-only）
   ├─ 000-template.md        # 方案模板（复制它开新迭代）
   └─ 001-*.md               # 第 N 次迭代
```

## 迭代约定

1. **一个迭代一份文档**：`docs/iterations/<三位编号>-<短横线主题>.md`，编号递增，**不删旧文档**。
2. 每份文档开工前写、收工后更新「完成情况」，做到**可追溯**。
3. 文档必含六要素：
   - **状态 / 日期**
   - **背景与目标**（为什么做）
   - **范围**（做 / 明确不做）
   - **方案**（每项的落地要点，含关键取舍）
   - **验收标准**（可验证，逐条勾选）
   - **风险与取舍**
4. 状态取值：`草稿` / `进行中` / `已完成` / `搁置`。

## 数据库变更约定（强约束）

**任何 schema 变更都必须带迁移，且迁移要能处理线上已有数据**——这是企业级平台的基本要求。

1. 迁移脚本放在 `apps/api/src/migrations/`，按序号命名（`001-xxx.sql`），**只增不改**：已上线的迁移脚本永不修改。
2. 迁移必须**幂等**（可重复执行不报错），并在平台库、应用库各自的初始化/升级流程中执行。
3. 破坏性变更（改结构、拆表）必须提供**数据搬迁**逻辑，不能只改 DDL 导致旧数据丢失。
4. `db:init` 负责：建表 + 执行所有未执行的迁移；迁移记录写入 `schema_migrations` 表。
5. 变更后两端（本地 + A 机）都要执行 `db:init`，并验证旧数据完好。

## 工作流程（体系化优化）

当需求是**体系化的优化或者一整块功能迭代**（而非零散小改动）时，遵循：

1. **先澄清**：用 `grill-me` 技能**逐个**提问，把需求、边界、验收标准问清楚，不急于给方案。
2. **再计划**：基于澄清结果制定方案（即本目录迭代文档的雏形）。
3. **确认后落文档并执行**：用户确认计划后，写入 `docs/iterations/<NNN>-<主题>.md`，然后开始执行。
4. **回溯**：功能自测 / 用户验收通过后，回看计划并更新文档（完成情况、偏差、后续项）。

> 零散小改动（文案、小 bug）不套此流程，直接处理即可。
